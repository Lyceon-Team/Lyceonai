### 2.1 One real drift, at object level not column level

`entitlements_profile_id_unique` is a **unique index** in production and a **table constraint** in
genesis.

```sql
SELECT 'pg_constraint' AS src, conname, pg_get_constraintdef(oid) FROM pg_constraint
WHERE conname='entitlements_profile_id_unique'
UNION ALL
SELECT 'pg_indexes', indexname, indexdef FROM pg_indexes
WHERE schemaname='public' AND indexname='entitlements_profile_id_unique';
```
```
pg_indexes | entitlements_profile_id_unique |
  CREATE UNIQUE INDEX entitlements_profile_id_unique ON public.entitlements USING btree (profile_id)
```
One row. **No `pg_constraint` row exists.**

- `genesis.sql:182` — `ALTER TABLE public.entitlements ADD CONSTRAINT entitlements_profile_id_unique UNIQUE (profile_id);`
- `20260809000000_…:21` — `CREATE UNIQUE INDEX IF NOT EXISTS entitlements_profile_id_unique …`

A `ADD CONSTRAINT … UNIQUE` produces both a `pg_constraint` row and a backing index. Production has
only the index, so **production was built by the later migration and genesis:182 did not take
effect there**. A fresh genesis replay produces a different object class than production holds.

**Practical impact: none for the write path.** `ON CONFLICT (profile_id)` resolves against a unique
index, and a unique constraint is backed by one, so the `upsert` at `server/lib/account.ts:353-370`
works either way. **The impact is on verification**: anything that reads `pg_constraint` — as the
Phase 1 SCL-D brief did — will not see it and will conclude the constraint is missing. That is
exactly how the brief got it wrong.

**Not queued as DDL** (nothing needs changing in production) but recorded here as a genesis defect:
`genesis.sql:182` should express the same object class the migration chain actually produces.

### 2.2 A second, benign genesis/production difference
